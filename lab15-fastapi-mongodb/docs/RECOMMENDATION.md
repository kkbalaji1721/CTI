# Lab 15.2 - Recommendation: document-level vs collection-per-tenant isolation

## Summary

| Criterion | Document-level (`tenant_id` field) | Collection-per-tenant |
|---|---|---|
| **Query isolation** | Logical only - isolation depends on *every* query containing `tenant_id`. One forgotten filter leaks data. Mitigate with a single query helper + tests. | Stronger: a query against `tasks_tenant_acme` physically cannot return another tenant's data. Authorization can also be granted per collection. |
| **Backup / restore granularity** | Hard: restoring one tenant means filtered export/import (`mongodump --query`) and merging, risking overwriting newer data. | Easy: dump/restore a single collection; drop a tenant = `drop()`. |
| **Schema evolution** | Easy: one collection, one index set, one validator; one migration for everyone. | Harder: N collections need N index/validator/migration runs; tenants can drift out of sync. |
| **Cross-tenant analytics** | Simple: one `$group` over one collection. | Needs `$unionWith` across N collections or application-side merging. |
| **Scalability** | Scales to thousands/millions of tenants - one set of indexes. | Each collection + its indexes consumes file handles/memory; becomes painful beyond a few thousand collections. |
| **Per-tenant tuning** | None (same indexes for all). | Possible (custom indexes, sharding or archiving for a big tenant). |
| **Performance (listing a tenant's tasks)** | With the `(tenant_id, created_at)` compound index the query is an index range scan - fast. | Same work, minus the `tenant_id` prefix. Difference is small and only visible at large scale. |

## When to choose which

**Prefer document-level isolation when**
- there are many tenants (hundreds to thousands+) of small/medium size,
- cross-tenant queries (analytics, admin dashboards) are frequent,
- schema and index changes must stay consistent across all tenants,
- you want the simplest operations story.

**Prefer collection-per-tenant (or database-per-tenant) when**
- a tenant's data must be backed up, restored, exported or deleted independently (e.g. "delete all my data" requests),
- regulation or contracts require strict data separation,
- a few large tenants need individual tuning or can be moved to their own cluster,
- the number of tenants is modest.

## Recommendation

Start with **document-level isolation** (what Lab 15.1 implements): it is the simplest and scales furthest. Enforce the
`tenant_id` filter in one place (`scope_filter`), take it from the JWT, and cover it with tests (see `tests/test_api.py`).
Migrate individual tenants - or everyone - to collection-per-tenant or database-per-tenant only when a concrete requirement
(independent backup/restore, compliance, a very large tenant) demands it. The migration scripts in `lab15_2/` show the path
and the validation step proves that no data leaks between tenants.
